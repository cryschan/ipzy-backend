# IPZY API Impact Analyzer

API 변경 시 영향 받는 범위를 분석하여 사이드 이펙트를 사전에 파악합니다.

## 사용 시점

- DTO 필드 추가/삭제/수정
- API 엔드포인트 변경
- 응답 구조 변경
- 에러 코드 변경
- 인증/권한 변경

## 워크플로우

```
API 변경 계획
       ↓
[1단계] 변경 대상 식별
       ↓
[2단계] 영향 범위 분석
       ↓
[3단계] 호환성 검토
       ↓
[4단계] 마이그레이션 가이드
       ↓
영향 분석 리포트 출력
```

## 1단계: 변경 대상 식별

### 분석 대상 유형

| 유형 | 파일 위치 | 영향 범위 |
|------|-----------|-----------|
| Request DTO | `dto/*Request.java` | 클라이언트 요청 |
| Response DTO | `dto/*Response.java` | 클라이언트 응답 파싱 |
| Controller | `controller/*.java` | URL, 메서드, 권한 |
| ErrorCode | `exception/*ErrorCode.java` | 에러 처리 로직 |

## 2단계: 영향 범위 분석

### 분석 항목

```
1. 해당 DTO/API를 사용하는 곳
   - Controller 메서드
   - Service 메서드
   - 테스트 코드

2. Swagger 문서 영향
   - @Schema 변경 필요 여부
   - 예시 값 업데이트

3. 프론트엔드 영향
   - 요청 파라미터 변경
   - 응답 파싱 변경
```

```markdown
# API 영향 분석 리포트

## 1. 변경 내용
- 변경 유형: 필드 추가 (하위 호환)
- UserResponse에 subscriptionStatus: String 필드 추가

## 2. 영향 범위

### 백엔드 영향
| 클래스 | 메서드 | 영향 |
|--------|--------|------|
| AuthController | me() | 응답에 새 필드 포함 |
| UserController | getProfile() | 응답에 새 필드 포함 |

### 테스트 영향
| 테스트 | 수정 필요 |
|--------|-----------|
| AuthControllerTest | assertion 추가 |
| UserServiceTest | from() 테스트 수정 |

### 프론트엔드 영향
- GET /api/auth/me 응답에 새 필드 추가
- GET /api/users/me 응답에 새 필드 추가

## 3. 호환성 검토
- Breaking Change: 없음 (필드 추가만)
- 기존 클라이언트: 정상 동작 (새 필드 무시)

## 4. 권장 사항
- 바로 배포 가능
- 프론트엔드에 새 필드 활용 안내
```

## 호환성 판단 기준

| 변경 유형 | Breaking Change | 이유 |
|-----------|-----------------|------|
| 필드 추가 | X | 기존 클라이언트 무시 가능 |
| 필드 삭제 | O | 기존 클라이언트 파싱 실패 |
| 필드 타입 변경 | O | 기존 클라이언트 파싱 실패 |
| 필드명 변경 | O | 기존 클라이언트 파싱 실패 |
| 필드 nullable 변경 | 상황에 따라 | null → non-null은 Breaking |
| 엔드포인트 URL 변경 | O | 기존 클라이언트 404 |
| HTTP 메서드 변경 | O | 기존 클라이언트 405 |
